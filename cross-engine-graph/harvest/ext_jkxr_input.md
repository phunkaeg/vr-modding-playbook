## 1. Input abstraction

OpenXR action sets — not raw per-frame polling of a device struct and not a synthesized generic gamepad. `TBXR_InitActions` builds one `XrActionSet` with actions bound per-interaction-profile (Touch, Index Knuckles, Vive wand, Pico 4) via `xrSuggestInteractionProfileBindings` (`JKXR\OpenXrInput.cpp:600-664` shows the Pico4 profile binding table: buttons, triggers, thumbstick, squeeze/grip, aim pose, haptics). Each frame, `TBXR_UpdateControllers` (`JKXR\OpenXrInput.cpp:758-786`) calls `TBXR_CheckControllers` → `TBXR_SyncActions` (`xrSyncActions`, `JKXR\OpenXrInput.cpp:696-710`) → `xrLocateSpace` for both the aim pose and grip pose of each hand, then reads button/axis state through `xrGetActionStateBoolean/Float/Vector2f` wrapper helpers (`JKXR\OpenXrInput.cpp:93,108,123`).

The result is copied into a mod-owned, engine-native struct: `ovrInputStateTrackedRemote` (buttons bitmask, joystick vector2, index/grip trigger floats) and `ovrTrackedController` (aim `Pose`, `GripPose`, `Velocity`) — declared/extern'd in `JKXR\VrInput.h:10-15` and populated in `JKXR\OpenXrInput.cpp:788-890`. This is the "landing" struct: `leftTrackedRemoteState_new/old`, `rightTrackedRemoteState_new/old`, `leftRemoteTracking_new`, `rightRemoteTracking_new`.

Notably, digital button state for the grip is itself *synthesized* from an analog axis with hysteresis: `leftTrackedRemoteState_new.GripTrigger` is read as a float (`squeezeForceAction` on Index, `squeezeAction` elsewhere) and turned into `xrButton_GripTrigger` only once it crosses `vr_engage_trigger` (default 0.7) and released only below `vr_release_trigger` (default 0.7, i.e. no hysteresis band by default), with per-device overrides `vr_engage_trigger_index`=0.7 / `vr_release_trigger_index`=0.05 for Index Knuckles specifically (`JKXR\OpenXrInput.cpp:839-873`). The main trigger is thresholded at a hardcoded 0.5 (`JKXR\OpenXrInput.cpp:876`, not a cvar).

## 2. Injection point

Two distinct paths, both ultimately feeding the client's `usercmd_t`/`viewangles`, and both running once per input-poll:

**(a) Continuous movement/orientation — direct struct writes, not synthetic keys.** `HandleInput_Default` (`JKXR\VrInputDefault.cpp:33-1216`) computes global floats `remote_movementForward/Sideways/Up`, `positional_movementForward/Sideways` (room-scale delta) and `vr.snapTurn` (`JKXR\VrInput.h:17-21`, `JKXR\VrClientInfo.h:76`). These are read by `VR_GetMove()` (`JKXR\windows\JKXR_SurfaceView.cpp:130-216`), which is called once per `CL_CreateCmd()` in the *engine's own* input file: `VR_GetMove(&new_move.forward, ...)` at `code\client\cl_input.cpp:702-703`. `CL_AdjustAngles()` then writes `cl.viewangles` directly — YAW is applied as a delta (`-= old_move.yaw; += new_move.yaw`, `code\client\cl_input.cpp:379-380`) so it composes with mouse yaw, while PITCH/ROLL are *overwritten* outright from the HMD (`cl.viewangles[PITCH] = new_move.pitch; ...[ROLL] = new_move.roll`, `code\client\cl_input.cpp:388-389`). Movement is injected by piggy-backing on the joystick-move slot: `CL_JoystickMove()` (repurposed for VR) does `cmd->forwardmove = ClampChar( cmd->forwardmove + (new_move.forward*127) + (new_move.pos_forward*127) )` and the same for `rightmove` (`code\client\cl_input.cpp:532-533`) — i.e. it *adds* onto whatever `CL_KeyMove()` already put there from real keyboard state, then clamps to the `usercmd_t` int8 range.

**(b) Discrete actions — synthetic console command text via `Cbuf_AddText`, not synthetic key events (except menu/UI).** `sendButtonAction()`/`sendButtonActionSimple()` (`JKXR\VrInputCommon.cpp:120-141`) `snprintf` a command string (e.g. `"+attack"`, prefixed with `-` on release) and push it through `Cbuf_AddText()` — the same text-console pipeline a bound key would use. Examples throughout `VrInputDefault.cpp`: firing (`sendButtonAction("+attack", ...)`, line 901), force powers (`"+useforce"`, line 1010), item-selector confirm (`"itemselectorselect"`, lines 367/387), thirdperson toggle (`"cg_thirdPerson 0/1"`, lines 522/541/550), scope enter/exit (`"enterscope"`/`"exitscope"`, lines 717/722/729), vehicle force yaw handled separately as a direct `vr.snapTurn` write (line 1024), etc. For menu/UI navigation specifically, real synthetic key events are queued via `Sys_QueEvent(0, SE_KEY, A_ESCAPE/A_TAB/A_MOUSE1, ...)` (`JKXR\VrInputDefault.cpp:290-296, 997-1002`, and `handleTrackedControllerButton()` in `JKXR\VrInputCommon.cpp:77-83`), and controller pointing is translated into an absolute mouse position fed to the existing UI mouse handler (`interactWithTouchScreen()` → `PortableMouseAbs()` → `CL_MouseEvent()`, `JKXR\VrInputCommon.cpp:144-165`, `JKXR\windows\JKXR_SurfaceView.cpp` `CL_MouseEvent` wrapper at line 152 of that file region).

## 3. Arbitration

No priority flag or mode switch — plain additive composition, ordered by call sequence inside `CL_CreateCmd()` (`code\client\cl_input.cpp:695-720`):
1. `VR_GetMove()` computes this frame's VR forward/side/yaw/pitch/roll (`cl_input.cpp:702`).
2. `CL_AdjustAngles()` applies VR yaw as a *delta* (undoing last frame's, applying this frame's) and *overwrites* pitch/roll outright (`cl_input.cpp:378-389`) — this runs before keyboard/mouse in the same call.
3. `CL_CmdButtons()`, then `CL_KeyMove()` sets `cmd->forwardmove/rightmove` from real keyboard state, overwriting the zeroed cmd (`cl_input.cpp:401-439`).
4. `CL_MouseMove()` runs next and *adds* mouse yaw/pitch on top of whatever VR just set (`cl.viewangles[YAW] -= m_yaw->value*mx`, `PITCH] += pitch*my`, `cl_input.cpp:584-609`) — so a player can still nudge view with a physical mouse even though the HMD sets the pitch baseline every frame.
5. `CL_JoystickMove()` runs last and *adds* the VR movement (`remote_movementForward/Sideways`, scaled by `move_speed`) onto whatever keyboard already contributed, then `ClampChar`s the sum (`cl_input.cpp:532-533`).

So: keyboard forwardmove and VR-joystick forwardmove **sum and saturate** (no keyboard lockout); mouse yaw and VR head-yaw **sum**; VR pitch/roll **overrides** mouse-set pitch/roll every frame (mouse pitch only survives until the next `CL_AdjustAngles()` call resets it from the HMD). There is no recency window or explicit real-vs-synthetic mode switch anywhere in these files.

Within the VR side itself there is a control-scheme switch, but it operates on which physical controller drives which logical role, not real-vs-synthetic arbitration: `vr_control_scheme` selects `RIGHT_HANDED_DEFAULT`(0) / `LEFT_HANDED_DEFAULT`(10) / `WEAPON_ALIGN`(99) which dispatches to `HandleInput_Default` or the dev-only `HandleInput_WeaponAlign` (`JKXR\windows\JKXR_SurfaceView.cpp:477-499`), and `vr_switch_sticks` swaps which physical thumbstick/buttons are "primary" vs "secondary" (`JKXR\VrInputDefault.cpp:67-107`).

## 4. Interaction

There is **no controller-pointed raycast for in-world objects** in this source. Two separate mechanisms exist, neither of which traces a ray from the controller into the world:

- **World "use" (doors, switches, pickups):** driven by a button/gesture mapped to the engine's own pre-existing `+use` console command (`JKXR\VrInputDefault.cpp:937,1192-1199`), which the underlying (non-VR) game code resolves via its own logic — not read/modified by JKXR, so how the engine picks the target entity is *not determined* from these files. JKXR's contribution is only *triggering* `+use`, via: (a) primary-thumbstick click (`sendButtonAction("+use", primaryButtonsNew & primaryThumb)`, line 937), or (b) an optional hand-distance gesture — moving either hand more than `vr_use_gesture_boundary` (default 0.35 m) away from the body triggers `+use`/`+altuse` (`JKXR\VrInputDefault.cpp:1173-1209`), gated by `vr_gesture_triggered_use` (default 1 = on).
- **Menu/UI pointing (2D screen laid into the VR world):** driven by controller *orientation*, not a ray-object intersection. `interactWithTouchScreen(menuYaw, controllerAngles)` (`JKXR\VrInputCommon.cpp:161-166`) maps controller pitch/yaw-relative-to-menu-yaw into a normalized 2D cursor position, which is submitted as an absolute mouse position (`PortableMouseAbs` → `CL_MouseEvent`) and consumed by the game's existing 2D UI system exactly as a desktop mouse would be. Which hand drives the cursor toggles on trigger-press (`JKXR\VrInputDefault.cpp:269-286`).
- **Weapon/saber aim** is likewise not a ray: the weapon's world orientation used for firing/attacking is the raw or gesture-adjusted controller pose (`vr.weaponangles[ANGLES_ADJUSTED/ANGLES_SABER]`, computed at `JKXR\VrInputDefault.cpp:134-238`), consumed downstream by the game's existing projectile/melee code (not in these files).

## 5. Locomotion (shipped modes, default marked)

- **Smooth thumbstick locomotion (DEFAULT / only continuous-movement mode shipped).** Off-hand (or swapped) joystick XY, deadzone+power-curve filtered (`nonLinearFilter`, deadzone 0.1, power 2.2, `JKXR\VrInputCommon.cpp:96-118`), rotated by `controllerYawHeading` and fed to `remote_movementForward/Sideways` (`JKXR\VrInputDefault.cpp:941-991`). Direction reference is controlled by `vr_walkdirection` (default `1`): `0` = move relative to the off-hand controller's yaw (`controllerYawHeading = offhandangles.yaw - hmd.yaw`), any non-zero value (**default**) = move relative to HMD facing (`controllerYawHeading = 0`, i.e. head-directed locomotion) (`JKXR\VrInputDefault.cpp:813-818`). In third-person with `vr_3rdperson_digital_direction` (default `1`) the analog vector is snapped to 8-way digital directions instead (`JKXR\VrInputDefault.cpp:961-968`).
- **Room-scale positional movement (always layered on top, not togglable).** Real head translation between frames is converted into forward/side movement via `positional_movementForward/Sideways`, scaled by `vr_positional_factor` (default `12`) and refresh-rate-corrected (`factor = (refresh/72.0f) * vr_positional_factor->value`, `JKXR\VrInputDefault.cpp:827-841`; dev-tool variant at `JKXR\VrInputWeaponAlign.cpp:141-151`). These are summed with the joystick contribution in `VR_GetMove`/`CL_JoystickMove` (`JKXR\windows\JKXR_SurfaceView.cpp:196-201`, `code\client\cl_input.cpp:532-533`).
- **Movement-speed toggle**, not a distinct locomotion mode but a speed multiplier cycled by pushing the primary stick fully forward: `vr.move_speed` cycles 0→1→2 (`JKXR\VrInputDefault.cpp:555-568`) mapped to `0.75` (Comfortable, **default** — `vr.move_speed = 1` is set at init but the comment at `VrClientInfo.h:51` labels 0=Comfortable(75%) as default UX state) / `1.0` (Full) / `0.5` (Walk) (`JKXR\VrInputDefault.cpp:970-982`). Forced to full speed (`1.0`) if `vr_always_run` (default `1`) or digital third-person direction is active (`JKXR\VrInputDefault.cpp:984-987`). *Minor inconsistency in source*: `VR_Init` sets `vr.move_speed = 1` with the comment "Default to full speed now" (`JKXR\windows\JKXR_SurfaceView.cpp:239`), while `VrClientInfo.h:51`'s comment calls `0` the default — the runtime default is `1` (Full) per the `VR_Init` assignment.
- **No teleport locomotion, no dash/blink locomotion, no arm-swinger locomotion found anywhere in this source tree.** (Confirmed via repo-wide case-insensitive search for "teleport" inside `JKXR\` — zero hits.)
- **Vehicle locomotion (JKA only, `#ifndef JK2_MODE`)** reuses the same forward/side channel but can source turn-yaw and forward-speed from controller angle instead of the stick, gated by `vr_vehicle_use_hmd_direction` (default `0`) and `vr_vehicle_use_controller_for_speed` (default `1`) (`JKXR\VrInputDefault.cpp:1015-1046`).

## 6. Comfort (shipped options, defaults)

- **Turn mode — `vr_turn_mode`, default `0` (snap turn).** `0` = snap everywhere, `1` = smooth only in third person, `2` = smooth in all modes (comment at registration, `JKXR\windows\JKXR_SurfaceView.cpp:245`; logic at `JKXR\VrInputDefault.cpp:1050-1051`).
- **Snap turn increment — `vr_turn_angle`, default `45` (degrees).** Applied as `vr.snapTurn -= /+= vr_turn_angle->value` once per stick-deflection-past-0.7 edge (debounced by `increaseSnap`/`decreaseSnap` latches so holding the stick doesn't repeat-fire) (`JKXR\VrInputDefault.cpp:1050-1093`). The same value also drives smooth-turn speed when snap is off: `vr.snapTurn -= (vr_turn_angle->value/25.0f) * primaryJoystickX` per frame (`JKXR\VrInputDefault.cpp:1086-1093`).
- **Comfort vignette — `vr_comfort_vignette`, default `0.0` (off).** Registered twice: once client-side (`JKXR\windows\JKXR_SurfaceView.cpp:275`, `android\JKXR_SurfaceView.cpp:357`) and once cgame-side (`gi.cvar(...)`, `codeJK2\cgame\cg_draw.cpp:2618` / `code\cgame\cg_draw.cpp:4127`). It is disabled outright if `<=0.0` or `>1.0` (`codeJK2\cgame\cg_draw.cpp:2619`), and when active it fades a screen-edge vignette in/out at `value*0.05` per frame while turning/moving (`codeJK2\cgame\cg_draw.cpp:2642-2650`). Shipped default is off.
- **Height calibration — system recenter, not a cvar or manual height cvar.** `TBXR_Recenter()` rebuilds the OpenXR `LOCAL`/`STAGE` reference spaces from the runtime's current head pose (`JKXR\windows\TBXR_Common.cpp:919-944`), called on session start (`TBXR_WaitForSessionActive`, line 946-954) and again whenever `ovrApp_HandleXrEvents` reports a runtime-driven recenter/origin-change event (line 950-952). Standing height for the IRL-crouch feature (`vr.maxHeight`) is captured once from the first valid HMD Y position and re-captured only after a recenter or an explicit reset (crouch-button press resets `vr.maxHeight = 0`, `JKXR\VrInputDefault.cpp:930`; capture logic at `JKXR\windows\JKXR_SurfaceView.cpp:82-86,94`). There is no player-facing "set my height" cvar in this source.
- **IRL (real-world) crouch — `vr_irl_crouch_enabled`, default `0` (off); `vr_irl_crouch_to_stand_ratio`, default `0.65`.** When enabled, physically crouching below `maxHeight * ratio` shrinks the player collision bounds proportionally (`codeJK2\game\bg_pmove.cpp:3532-3591`, mirrored in `code\game\bg_pmove.cpp:5790-5849`); minimum height is clamped so players can't crawl below the ratio threshold.
- **Crouch input mode — `vr_crouch_toggle`, default `0` (hold, not toggle).** `0` = crouch held only while off-hand-thumbstick button is pressed (`+movedown` sent on both press and release); `1` = each press toggles `vr.crouched` (`JKXR\VrInputDefault.cpp:913-931`).
- **Cinematic comfort — `vr_immersive_cinematics`, default `1` (on).** When on, cutscenes render immersively rather than dropping to the flat "screen layer" (`VR_UseScreenLayer()` check at `JKXR\windows\JKXR_SurfaceView.cpp:30-46`; cvar registration `JKXR\windows\JKXR_SurfaceView.cpp:258`, also force-set `true` at `VR_Init`, `JKXR\windows\JKXR_SurfaceView.cpp:238`).
- **Virtual screen distance for the flat-menu layer — `vr_screen_dist`, default `3.5`**, combined as `2.0f + vr_screen_dist->value` (`JKXR\windows\JKXR_SurfaceView.cpp:48-51,259`) — affects how far away 2D menus/cinematics are placed, a comfort-adjacent but not a turn/vignette setting.

No explicit "vignette strength presets" or "comfort mode" master switch was found — `vr_comfort_vignette` is a single continuous 0.0–1.0 float.

## Transferable lessons
- **Piggyback VR movement on an existing "extra input" slot instead of writing a parallel movement path.** JKXR reuses the engine's disused `CL_JoystickMove()` to *add* VR stick output onto whatever keyboard already wrote, then clamps once (`code\client\cl_input.cpp:532-533`). This gets keyboard+VR arbitration "for free" (simple additive saturation) instead of requiring a hand-written priority system — worth checking whether a target engine already has an underused input channel (joystick/gamepad slot) that can be repurposed the same way.
- **Let VR override view *angles* every frame rather than merging deltas, but let real-mouse pitch/yaw still nudge on top.** `CL_AdjustAngles()` sets pitch/roll straight from the HMD and only deltas yaw (`code\client\cl_input.cpp:378-389`), and mouse-move still runs afterward and adds to both. This keeps head tracking authoritative for orientation without silently disabling desktop-mouse fallback, useful when a codebase must support flat-screen and VR from the same binary.
- **Synthesize digital buttons from analog triggers with separate per-device engage/release thresholds, not one global boolean cutoff.** The grip-to-`xrButton_GripTrigger` hysteresis logic (`JKXR\OpenXrInput.cpp:839-873`) uses distinct `vr_engage_trigger`/`vr_release_trigger` cvars and a per-controller-type override for Index Knuckles, because Knuckles' capacitive/force sensing behaves differently from a physical squeeze click — a reminder to expose engage/release as separate tunables (not one deadzone) whenever mapping analog force sensors to discrete game actions.
- **Route discrete VR actions through the existing console-command pipeline (`Cbuf_AddText`) instead of a bespoke action-dispatch table.** Every VR button press becomes literally the same string a keybind would produce (`"+attack"`, `"cg_thirdPerson 1"`, etc., `JKXR\VrInputCommon.cpp:120-141`), which means every downstream system (server-side anti-cheat, demo playback, mods) needed zero changes to understand VR input. If a target engine has a console/cvar command system, prefer this over inventing a new input-event type.
- **Don't build a controller-ray interaction system if the base game already resolves "use" contextually.** JKXR never raycasts from the controller; it just triggers the same `+use` the original keyboard game used, plus an optional reach-gesture as an alternate trigger (`JKXR\VrInputDefault.cpp:1173-1209`). For a flat game whose "interact" is already proximity/facing-based, wiring VR buttons to the existing action can be far less work than reimplementing physical-ray picking.
- **Base comfort defaults matter and were conservative on ship:** snap turn (not smooth) at 45°, vignette *off* by default, IRL crouch *off* by default, always-run *on* by default. This mix — cheap/aggressive comfort features (snap turn) on, more experimental ones (vignette, IRL crouch) off — is a reasonable pattern for a first VR pass on a fast-paced action game.
- **Height/floor calibration was left to the OpenXR runtime's recenter, not reimplemented.** `TBXR_Recenter()` just recreates `LOCAL`/`STAGE` reference spaces from the runtime (`JKXR\windows\TBXR_Common.cpp:919-944`) rather than the mod tracking its own "floor offset" cvar — leaning on the platform's own room-setup/recenter gesture avoids an entire class of stale-calibration bugs.
