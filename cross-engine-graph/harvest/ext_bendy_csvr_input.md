# CSVR

## 1. Input abstraction
Not determined at the true source level (SteamVR/OpenXR action-set code, raw polling, device sync — all inside the missing `xash3d-fwgs` engine fork). What is determined from the game DLL: controller/HMD state arrives as **already-resolved scalar values in ordinary engine cvars**, read via `gEngfuncs.pfnGetCvarFloat("vr_...")` / `pfnGetCvarString(...)`. Confirmed cvar names actually read by the game DLL: `vr_gamemode`, `vr_spectator`, `vr_shielded`, `vr_zoomfix`, `vr_6dof`, `vr_hand_swap`, `vr_hand_x/y/z`, `vr_hand_pitch/yaw/roll`, `vr_weapon_x/y/z`, `vr_weapon_pivot_x/y/z/pitch/yaw/scale`, `vr_weapon_pivot_name`, `vr_weapon_calibration_update`, `vr_offset_x/y/z`, `vr_weapon_roll` (`cl_dll/StudioModelRenderer.cpp:424-1789`, `cl_dll/ammo.cpp:1024`, `cl_dll/view.cpp:901`). The game DLL also **writes back** into that same cvar namespace — `vr_shielded` (`cl_dll/cs_wpn/cs_weapons.cpp:601`), `vr_spectator` (`cl_dll/hud_spectator.cpp:461`), `vr_weapon_calibration_update`/`vr_weapon_pivot_*` (`cl_dll/StudioModelRenderer.cpp:1555,1580-1586`), and `vr_haptics_weapon` (`dlls/wpn_shared/wpn_m3.cpp:128`). So the boundary contract is a **bidirectional shared-cvar bridge**, not an action-set API surfaced in this repo.

## 2. Injection point
`cl_dll/input.cpp:644-729` (`CL_CreateMove`) and its `IN_Move` (mouse) callee are **byte-for-byte the stock GoldSrc SDK path** — `cmd->forwardmove/sidemove/upmove` come from `kbutton_t` states (`in_forward`, `in_moveleft`, `in_right`, etc., `input.cpp:664-694`), and `cmd->buttons = CL_ButtonBits(1)` (`input.cpp:724`). No VR-specific edits exist in this function. `pm_shared/` (player movement prediction) has **zero** matches for `vr_`/`VR` (grepped, confirmed empty) — the prediction/movement core is completely untouched. Weapon firing uses the ordinary `pev->button & IN_ATTACK`/`IN_ATTACK2` bitmask unmodified (`cl_dll/cs_wpn/cs_weapons.cpp:592,612`). **Not determined**: the actual mechanism by which a controller thumbstick/trigger becomes a `kbutton_t` state or a `usercmd` button bit — that translation must happen upstream, inside the missing engine fork (most likely by the engine driving the same `+forward`/`+attack`-style console command bindings a keyboard would, since that is the only integration seam visible from the SDK side, but this is inference, not evidenced by source in this checkout, so it is NOT claimed as fact). What is confirmed is the shape of the answer to the prompt's specific question: **VR movement/attack input, whatever produces it, is funneled through the same `usercmd_t`/`CL_CreateMove`/prediction pipeline as KBM/gamepad — no parallel movement path exists in the visible game-logic layer.**

## 3. Arbitration
Not determined how the engine decides real KBM/gamepad vs synthetic VR input (that logic is in the missing engine). Game-DLL-side evidence of a flat/VR mode switch exists: `vr_gamemode` gates whether weapon/hand models are hidden off-screen (flat mode) or VR-positioned (`cl_dll/StudioModelRenderer.cpp:424-434`), i.e., the same binary supports a non-VR "gamemode" toggled by a single cvar, but the arbitration mechanism itself is not visible.

## 4. Interaction
No "pointing/grabbing/using" ray-cast code exists anywhere in `dlls/` or `pm_shared/` — CS 1.6's `+use` is unmodified vanilla eye-trace `IN_USE`/`IN_DUCK` (`cl_dll/input.cpp:453-472`, comment "Not in VR" at lines 456/469 marking two spectator-only behaviors deliberately skipped in VR, nothing else). Interaction is really a **rendering/weapon-attachment problem, not a raycast problem**: weapon and off-hand models are transformed onto the tracked-hand pose every frame via `UpdateVRHandTransform`/`UpdateVRWeaponTransform` (`cl_dll/StudioModelRenderer.cpp:1651-1790`), driven entirely by the `vr_hand_*`/`vr_weapon_*` cvars above. Per-weapon pivot/offset calibration is persisted to `/sdcard/xash/cstrike/models/vr_weapons.cfg` and re-read on model change (`StudioModelRenderer.cpp:1524-1588`); shipped defaults for that file are listed below. Not determined: how/whether an actual aiming or use-trace ray is cast from the hand (no such code found in the checked-out source).

## 5. Locomotion modes shipped, and which is DEFAULT
Not determined — locomotion (thumbstick move / teleport / dash) is entirely engine-owned and not present in this checkout. The only locomotion-adjacent, visible logic is a **spectator free-look mode** toggle (`vr_spectator`, driven by `g_iUser1` at `cl_dll/hud_spectator.cpp:461`) and the `vr_6dof` flag that enables applying `vr_offset_x/y` (as opposed to only `vr_offset_z`) to weapon-model camera offset (`StudioModelRenderer.cpp:1779-1784`), implying a non-6DOF fallback mode exists, but its default and full effect are not determined from source here.

# BendyVR

## 1. Input abstraction
SteamVR/OpenVR **action-based** input via the SteamVR Unity Plugin (`Valve.VR` / `SteamVR_Input`), organized into named action sets `DominantHand`, `NonDominantHand`, `MovementHand`, `RotationHand` (`BendyVR_5/src/VrInput/ActionInputs/ActionInputDefinitions.cs:8-29`). Action sets are activated once at startup: `foreach (var actionSet in SteamVR_Input.actionSets) actionSet.Activate();` (`BendyVR_5/src/VrInput/BindingsManager.cs:61-64`, called from `Awake` at line 44-47). Controller state lands in a thin wrapper class `ActionInput<TAction>` (`BendyVR_5/src/VrInput/ActionInputs/ActionInput.cs:1-72`) wrapping `SteamVR_Action_Boolean`/`SteamVR_Action_Vector2`, which resolves the correct hand (`HandSource`, lines 15-31) based on `VrSettings.LeftHandedMode`/`SwapSticks`, and exposes `AxisValue`/`ButtonValue`/`ButtonUp`/`ButtonDown` (lines 33-37), each gated on `Action.active` (lines 49-67). `BindingsManager` (`BindingsManager.cs:12-107`) also maps these `IActionInput`s onto the game's own `VirtualKey` enum (a `Dictionary<string, IActionInput> ActionMap`, lines 14-36) for input-prompt/UI-glyph purposes only.

## 2. Injection point
Not a `usercmd`-style model (this is a Unity third-person/first-person single-player game, not a client/server usercmd engine). Injection is via **Harmony prefix patches on the game's own `PlayerInput` static query methods** — `PlayerInput.Any/Attack/SeeingTool/AttackHold/Run/Jump/Pause/MoveX/MoveY/LookX/BackOnPressed/InteractOnPressed/InteractOnReleased` are each intercepted with `[HarmonyPrefix]`, their `__result` set from the matching `ActionInputDefinitions.*` value, and the original method skipped (`return false`) (`BendyVR_5/src/VrInput/Patches/PlayerInputPatches.cs:15-129`, e.g. `MoveX`→`ActionInputDefinitions.MoveX.AxisValue` at lines 81-86). Movement itself is applied directly in `VRPlayerController.FixedUpdate`→`Move()` via `CharacterController.Move()` using `mPlayerController.m_Input.x/y` (populated from the same patched `PlayerInput.MoveX/MoveY`) (`BendyVR_5/src/Player/VRPlayerController.cs:1026-1071`). The stock `PlayerController.FixedUpdate`/`Update` are disabled outright via another Harmony prefix returning `false` (`BendyVR_5/src/Player/Patches/PlayerControllerPatches.cs:16-22`), so the VR controller class fully owns the per-frame movement/rotation tick.

## 3. Arbitration
Real mouse input is hard-disabled, not blended: `Input.GetAxis("Mouse X"/"Mouse Y")` is Harmony-patched to always return 0 (`BendyVR_5/src/VrInput/Patches/MousePatches.cs:19-29`). Real keyboard/gamepad input to gameplay is also fully superseded — every `PlayerInput` query is replaced unconditionally by the SteamVR action value (section 2), so there is no runtime fallback/merge between real and synthetic input for gameplay actions. For UI/menu navigation, `InputUtil.GetInputX/GetInputY` (used by the game's own `InControl`-based menu system) are patched to blend VR d-pad-style actions (`UiUp`/`UiDown`/`Next`/`Previous`) with the movement joystick as a secondary source (`BendyVR_5/src/VrInput/Patches/InputManagerPatches.cs:74-172`). Separately, because some game logic branches on `GameManager.HasController` (gamepad presence) via an inline function that can't be patched directly, the mod injects a **dummy `InputDevice`** into `InputManager.devices` so that check reports true (`InputManagerPatches.cs:57-69`) — i.e., VR is arbitrated by impersonating a gamepad at the device-list level.

## 4. Interaction
Pointing/using is a **sphere-cast from the off-hand laser**, not a thin ray: `InteractableInputController.UpdateInteraction` is replaced by a Harmony prefix that does `Physics.SphereCast(origin, 0.3f, direction, out hitInfo, distance, ...)`, calling `Interact()` on hit when `PlayerInput.InteractOnPressed()` is true (`BendyVR_5/src/Player/Patches/PlayerControllerPatches.cs:31-70`). It's driven every `Update` from the laser's transform: `mPlayerController.m_Interaction.UpdateInteraction(mLaser.transform.position, mLaser.transform.forward)` (`BendyVR_5/src/Player/VRPlayerController.cs:763`). The laser (`VrLaser`) is parented to the **non-dominant** hand (`VRPlayerController.cs:143`, re-parented on handedness swap at line 183), and its visibility (not its function — the cast always runs) is gated by `VrSettings.ShowLaserPointer` and non-zero `Interact` axis value (`BendyVR_5/src/LaserPointer/VrLaser.cs:48-54`). The interact button is `NonDominantHand.Interact`, default binding comment "Default: B" (`ActionInputDefinitions.cs:9`).

## 5. Locomotion modes shipped, and which is DEFAULT
Only **continuous smooth joystick locomotion** is actually implemented — `VRPlayerController.Move(float speed)` applies `CharacterController.Move()` every `FixedUpdate` using the movement-hand joystick axes (`VRPlayerController.cs:1026-1071`), direction is either **head/camera-relative (DEFAULT)** or **controller-relative**, chosen by `VrSettings.ControllerBasedMovementDirection` (config default `false`, so DEFAULT = head-based direction) (`VrSettings.cs:92-93`, applied at `VRPlayerController.cs:1030-1033`). A `VrSettings.Teleport` config entry exists ("Fixed camera while moving | 'Teleport' locomotion. Camera stays still while player moves", default `false`, `VrSettings.cs:86-87`) but **no code anywhere in the mod reads `VrSettings.Teleport`** (grepped across the whole repo, zero matches) — despite its name and description, it is a dead/unwired config option in this source snapshot, i.e., true teleport locomotion is not actually shipped/functional, only smooth locomotion is.

## 6. Comfort options shipped, and their DEFAULTS
- Turning mode: **Snap turning, DEFAULT ON** (`VrSettings.SnapTurning`, default `true`, `VrSettings.cs:80-81`); when off, continuous **smooth turning** is used instead (`VRPlayerController.cs:945-951, 970-996`).
- Snap turn angle: `VrSettings.SnapTurnAngle`, enum `SnapTurnAngleOption {23,30,45,60,90}`, **DEFAULT 45°** (`VrSettings.cs:82-83`, enum at lines 21-28). Snap turn fades to black then back via `coreVR.FadeToBlack()`/`FadeToClear()`, fade duration `FadeOverlay.Duration = 0.1f` (`FadeOverlay.cs:10`, used at `VRPlayerController.cs:958-966,1016-1022`).
- Smooth rotation speed: `VrSettings.SmoothRotationSpeed`, enum `{VerySlow=1,Slow=2,Default=3,Fast=4,VeryFast=5}`, **DEFAULT = Default(3)** (`VrSettings.cs:84-85`, enum lines 12-19), multiplies a base 50°/s (`smoothRotationBaseSpeed = 50f`, `VRPlayerController.cs:69,985-989`).
- "Fixed camera during animations": default `false` (`VrSettings.cs:88-89`).
- "Teleport" (camera-stays-still-while-moving comfort option, misleadingly named): default `false`, and unwired (see section 5).
- Head bob: `VrSettings.EnableHeadBob`, **DEFAULT OFF (false)** (`VrSettings.cs:94-95`), applied in `Move()`/`FixedUpdate` only when true (`VRPlayerController.cs:864-867,1118-1121`).
- Room-scale body follows headset (drift vs. comfort tradeoff): `VrSettings.RoomScaleBodyPosition`, **DEFAULT ON (true)** (`VrSettings.cs:90-91`).
- Particles/dust: `VrSettings.EnableParticles`, default `true` (`VrSettings.cs:96-97`) — listed under the "Comfort" category alongside vection-related settings, presumably for motion-sensitive players to reduce visual noise, though not itself a locomotion comfort setting.

## 7. Configurable vs hardcoded
Configurable via BepInEx `ConfigFile` (`VrSettings.SetUp`, `VrSettings.cs:75-114`), grouped into categories `Controls`, `Comfort`, `Player Body`, `Rendering`: `SnapTurning`, `SnapTurnAngle`, `SmoothRotationSpeed`, `Teleport`, `FixedCameraDuringAnimations`, `RoomScaleBodyPosition`, `ControllerBasedMovementDirection`, `EnableHeadBob`, `EnableParticles`, `LeftHandedMode`, `ShowLaserPointer`, `SwapSticks`, `HeightOffset`, `VelocityTrigger`, `AngularVelocityTrigger`, `ShowLegacySteamVRHands`. ## Transferable lessons
- **Keep the movement/prediction core untouched; feed VR input through the existing funnel.** CSVR's `pm_shared` (player-movement prediction) has zero VR-specific code, and `CL_CreateMove`/`IN_Move` in `cl_dll/input.cpp:644-729` are stock GoldSrc — VR movement, whatever produces it, still results in a normal `usercmd_t`. For any `usercmd`/prediction-shaped engine in this playbook, the pattern to imitate is: don't touch the prediction/movement code path at all, only change what feeds the buttons/axes upstream of it.
- **A flat, bidirectional cvar bridge is a viable substitute for a typed action-set API at the engine/game-DLL boundary.** CSVR's engine (not in this checkout) and game DLL communicate 6DOF pose, mode flags, and haptics purely through named cvars (`vr_hand_x/y/z`, `vr_gamemode`, `vr_haptics_weapon`, etc., `cl_dll/StudioModelRenderer.cpp:424-1789`), read and written from both sides. This is a low-friction way to cross an engine/mod boundary when you can't share a header-level action-set struct.
- **Harmony-prefixing the game's own input-query methods, not injecting into the input library, is a clean and total injection point.** BendyVR intercepts `PlayerInput.MoveX/MoveY/Attack/Jump/...` directly (`PlayerInputPatches.cs:15-129`) rather than trying to feed synthetic events into `InControl`/Unity's input system — this guarantees VR values are the only values the game ever sees for those calls, with no merge/precedence logic needed.
- **Disable the competing real-input source outright rather than trying to arbitrate it.** BendyVR hard-zeroes `Input.GetAxis("Mouse X"/"Mouse Y")` (`MousePatches.cs:19-29`) instead of trying to detect and prioritize VR vs. mouse per-frame — arbitration-by-elimination is simpler and shipped.
- **When a game logic-gates on "is a controller connected," fake the device rather than patch every call site.** BendyVR injects a dummy `InputDevice` into `InputManager.devices` (`InputManagerPatches.cs:57-69`) because the real check was an inline function it couldn't Harmony-patch — worth remembering as a fallback technique when a target check is unreachable.
- **Weapon/prop attachment onto tracked-hand pose is a rendering-transform problem, solved with per-object calibration data, not a raycast/physics problem.** CSVR persists per-weapon-model pivot offsets to a plain CSV-like config file (`vr_weapons.cfg`) with a hardcoded fallback (`StudioModelRenderer.cpp:1524-1588,1558-1563`) rather than hand-authoring an attachment point per asset up front — useful for mods retrofitting VR onto large pre-existing weapon/prop rosters.
- **A config option can exist, be documented, default to off, and still do nothing.** BendyVR's `VrSettings.Teleport` is fully defined and described as a locomotion/comfort feature (`VrSettings.cs:86-87`) but has zero call sites anywhere in the mod — a reminder to verify a shipped default is actually wired before trusting it as evidence of what "worked," and a caution for this playbook to treat config-file presence alone as insufficient proof of a working feature.
- **Both mods default to the less-nauseating turning method (snap turn) and default the more comfort-costly locomotion input (head-relative vs. hand-relative direction) toward the simpler/safer option**, matching the broader pattern in this playbook that shipped VR ports converge on snap-turn-by-default; BendyVR additionally defaults head bob OFF (`VrSettings.cs:94-95`) — another comfort-conservative default worth carrying into the playbook's cross-engine defaults table.
